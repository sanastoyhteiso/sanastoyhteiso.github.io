# Sanastoyhteisö V3 Development — безопасное подключение новой Firestore

Дата: 2026-11-03. Новый проект создан владельцем. Известный **единственный допустимый Project ID**: `sanastoyhteiso-v3-development`. Создана Firestore **(default)** на Spark. Приложение Google Auth Pilot на телефоне показало «Вход подтверждён». Старый Firebase `riveria-sanasto-community-test` и действующий сайт `https://sanastoyhteiso.github.io/` трогать ЗАПРЕЩЕНО.

## Состояние работ

- Правила только в GitHub draft PR #8: `staging/backend/firestore.v3-development.rules`.
- Эмуляторная проверка: `staging/tests/firestore-v3-development.test.cjs`, fake-проект `demo-sanastoyhteiso-v3-development`, без сети к Firebase и без реальных пользователей. GitHub Actions выполняет также все прежние тесты.
- Транзакционный профильный адаптер: `staging/backend/rs-v3-firestore-profile-store.js` и `staging/tests/v3-firestore-profile-store.test.cjs`; **не включён в опубликованный сайт** и не производит реальных записей, пока правила не опубликованы и не проверены.
- Существующий публичный v3-classic всё ещё полностью офлайн и не пишет в Firestore. У Google Auth Pilot пока только аутентификация без базы.
- Любые слова и изображения пациентов запрещены в тестовых данных. Использовать только вымышленные учётные записи/словарные примеры.

## Что разрешат правила после отдельной публикации

1. `users/{uid}`: только подтверждённому владельцу профиль с `alias`, `publicStats`, `learned`, `updatedAt`. Новый профиль по умолчанию `publicStats=false, learned=0`; чужие пользователи его **не читают**. Изменения проверяются, удаление запрещено.
2. `settings/{uid}`: только владельцу, с ограниченной схемой. Удаление запрещено.
3. `sync_v3/{uid}/events/{eventId}`: события обучения только своему UID, строго проверенные и **неизменяемые**. Поддерживаются `answer`, `learned_set`, `favorite_set`, `word_upsert`, `word_delete`, включая настоящий формат личных слов старого сайта. Чужой UID и неподтверждённая почта блокируются.
4. `sync_v3/{uid}/state/baseline`: разрешено читать владельцу уже существующую запись. **Импорт базового снимка заблокирован** до свежей резервной копии и отдельного подтверждения владельца, чтобы исключить случайное затирание данных.
5. `libraries_v3/{libraryId}` и `.../terms/{termId}`: владелец создаёт/редактирует только **приватную** библиотеку, отдельно переводит в `public`. После публикации содержимое неизменно; чужую приватную библиотеку не прочитать. Все новые слова передаются только через `fi,ru,en,cat`, без email и оценок. Для будущих исправлений планируется публикация новой версии (не скрытая подмена).
6. `library_subscriptions_v3/{uid}/items/{libraryId}`: подписка только по решению владельца, доступ только собственному UID, нельзя подписаться на чужую приватную/несуществующую коллекцию. Отключение `enabled=false` не удаляет ранее выученные слова.
7. `site_admin`: чтение агрегатов только с серверно подтверждённым `admin` claim; даже админ не может записывать из браузера. Нет пользовательских административных прав, пока специально не назначены.
8. По умолчанию **все неизвестные коллекции и действия запрещены**.

### Почему профили не открываются публично сразу

Флаг `publicStats` пока может быть сохранён как желание пользователя, но не даёт другим доступа к полному `users/{uid}`. Иначе при чтении профиля могли бы раскрываться будущие личные поля. Для публичного каталога позднее потребуется отдельное представление с разрешёнными атрибутами и тестами приватности.

## Действие в Firebase Console — ТОЛЬКО после зелёных тестов

1. Внимательно проверить, что выбран проект **Sanastoyhteiso V3 Development**, ID `sanastoyhteiso-v3-development`. Если открыт любой другой проект — остановиться.
2. **Cloud Firestore → Database → (default) → Rules**. Сначала сфотографировать/скопировать действующие правила в безопасное место. Если на новой базе виден `allow read, write: if true` или срок действия Test mode — сообщить и срочно заменить на `false`.
3. Открыть файл `staging/backend/firestore.v3-development.rules` в GitHub и скопировать **весь текст целиком**, начиная с `rules_version = '2';` (включая комментарии допустимо).
4. В редакторе Firebase Rules вставить вместо начального `deny all` **только в новом проекте**. Визуально проверить сохранность всего файла, затем **Publish**. Это меняет права доступа к новой тестовой базе, поэтому выполняется отдельно и только владельцем/авторизованным инструментом.
5. Прислать скриншот вкладки Rules после публикации, без учётных данных, пользовательских ID и токенов. Не нажимать «Start collection», не создавать персональные документы вручную.
6. Далее открыть отдельный проверочный интерфейс и убедиться, что новый пользователь может создать свой профиль, но не увидеть чужой. **Код, который пишет реальные профили, пока не опубликован**; он будет включён лишь после проверки правил.

**Нельзя:** использовать Cloud Functions/Admin SDK с секретными ключами для обхода правил в браузере, копировать реальные слова из старого проекта, удалять старый Auth или изменять продакшн; нельзя объявлять готовую синхронизацию до двухустройственных испытаний и восстановления из независимой резервной копии.

## Финальный переход

Планируем сохранить прежний Firebase Authentication/UID для уже зарегистрированных пользователей, а отдельный проект разработки использовать только для испытаний. Финальное подключение и миграция профилей/словарей/результатов — отдельный этап с проверенным восстановлением и откатом, без потери старых данных.
