# Sanastoyhteisö 3.0 — две независимые версии и тестовое подключение

## Адреса и границы

**РАБОЧИЙ, неизменяемый при тестировании:** https://sanastoyhteiso.github.io/ (репозиторий sanastoyhteiso/sanastoyhteiso.github.io, ветка main).

**НОВАЯ ВЕРСИЯ, для разработки:** https://velardream-ctrl.github.io/riveria-sanasto-community-test/ (отдельный репозиторий velardream-ctrl/riveria-sanasto-community-test, тестовая главная страница переводит в /v3-classic/; текущая версия без настоящего входа, с публичным словарём и вымышленными результатами). GitHub не предоставляет гарантию немедленной публикации после commit: проверить страницу в настоящем браузере, в том числе на iPhone и старом Safari.

Исходники разрабатываются в черновом PR #8 основной кодовой базы, в папке staging; результаты успешно проверенных тестов вручную копируются в отдельный тестовый репозиторий. PR не сливать в основной main.

Исходная главная страница тестового репозитория ранее включала Firebase Auth и config.js проекта **riveria-sanasto-community-test**; этот проект, несмотря на слово test, используется действующим сайтом! Старый вход тестового репозитория нельзя использовать для безопасных испытаний реальной новой синхронизации. Новая главная страница тестового репозитория заменена на безопасный переход в /v3-classic/, который снимает старую регистрацию service worker тестового репозитория и удаляет лишь его старые кэши. Никаких пользовательских данных и Firebase при этом не удаляется. Историю старого index.html можно найти в GitHub history.

**Текущий v3-classic — безопасная UI-демонстрация, не готовая облачная версия.** На странице есть Mediatri, FI/EN/RU, карточки и тесты, но Firebase/Google Drive/реальные библиотеки там намеренно отключены (строгая CSP connect-src 'none'). Не заявлять о настоящей синхронизации, общей библиотеке или авторизации администратора до их реальной реализации.

## Что нужно для подключения новой версии (не использовать существующий Firebase)

1. Создать **совершенно другой Firebase project** в своей Firebase Console. Предлагаемое имя проекта/ID должно начинаться с \`sanastoyhteiso-v3-\`, например \`sanastoyhteiso-v3-lab-<уникальный_суффикс>\`; окончательный свободный ID придёт из Firebase Console. Название — лишь конвенция; проект на самом деле должен быть совершенно новым и не иметь общих данных с \`riveria-sanasto-community-test\`.
2. Зарегистрировать внутри нового проекта отдельный Web App; получить его **публичную Web SDK конфигурацию** (projectId, authDomain, apiKey, appId). Никогда не передавать закрытые ключи администратора, service account JSON, пароли, токены или 2FA в чат или репозиторий.
3. Включить Google Sign-in именно для нового проекта, добавить \`velardream-ctrl.github.io\` в Authentication > Settings > Authorized domains. В том числе проверить pop-up на настоящем iPhone и iPad; старый iOS12 может требовать дополнительной совместимости.
4. Создать новую Firestore \`(default)\` в отдельном проекте (по возможности регион \`europe-north1\`, но выбрать его надо до создания и сверить доступные варианты). В ней не должно быть настоящих записей, резервных копий или персональных результатов с рабочего сайта.
5. Разворачивать только проверенные Firestore Security Rules из staging после ручной проверки, соответствия целевой схеме данных и отдельного теста на этот новый проект. Начать с двух **вымышленных** аккаунтов, проверки owner-only data и публичной/частной библиотеки; убедиться, что чужие записи недоступны. Учётные данные Firebase Admin ни при каких условиях не публиковать. До этого этапа подключение реального удалённого хранилища не разрешено.
6. Перед первым реальным запросом клиент должен пройти \`staging/backend/v3-staging-project-guard.js\`: точные origin/path, проект из нового семейства, проверка его ожидаемого projectId, строгий запрет ID рабочей базы. Сам guard — дополнительная защита, не замена изоляции проектов и серверным правилам.
7. Только после полной проверки серверной авторизации, изолированных библиотек, Firestore events + offline и повторов можно разрешить на тестовом сайте новый Cloud Sync. Сохранять привычный UI без перехода к упрощённому демонстрационному дизайну.

## Личные библиотеки и управление

Для всех пользователей сохраняются старые разделы:
- **Библиотека**: личные словари, общедоступный каталог Riveria, создание/публикация, подписки на чужие словари, подключение по ID. Подписка добровольная; обновления подключённой библиотеки не стирают личный прогресс. Будущий источник словарей — Firestore, Google Sheets — резервные копии, а не обязательная таблица каждого читателя.
- **Данные**: личный аккаунт, состояние и настройки синхронизации, JSON/Sheets резервные копии и восстановление. Обычное меню доступно всем.
- **Данные → Настройки сайта**: только серверно подтверждённый администратор. В текущем v3-classic показан исключительно read-only макет, цифры вымышлены.

Администратор не получает право свободно читать личные ответы и приватные слова пользователей. Сбор агрегатов без идентифицирующих данных — отдельная задача.

## Переключение основного сайта — только в конце

Не пытаться «переименовать» адрес \`sanastoyhteiso.github.io\` в адрес тестового пользователя: URL user/organization GitHub Pages привязан к владельцу репозитория. После принятия новой версии переносим **проверенные файлы** в основной репозиторий, только после свежих проверенных резервных копий личных JSON/словарей/Sheets и детального переноса данных. Далее выполнить ограниченный проверочный запуск, rollback-проверку, только потом обновить \`main\`. Старый адрес при этом сохраняется. Никакой необходимости менять домен или уничтожать историю сайта нет.

**Нельзя:** трогать рабочий \`main\`, правила Firestore, реальные записи пользователей, экспортировать персональные словари без разрешения, отключать существующую синхронизацию Drive или вливать draft PR до отдельного утверждённого безопасного релиза.
