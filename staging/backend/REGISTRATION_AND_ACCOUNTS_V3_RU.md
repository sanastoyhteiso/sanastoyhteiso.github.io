# Sanastoyhteisö 3.0 — регистрация, профили, сохранение аккаунтов

## Обязательное требование

Регистрация не удаляется. Сохраняем прежний Google-вход с Firebase Authentication, подтверждение email, личный псевдоним, добровольную публикацию статистики, отдельные слова и учебные результаты. Повторный вход не создаёт новый профиль и не сбрасывает персональные данные. У каждого человека свой прогресс, в том числе на семейном устройстве.

Первый Google sign-in автоматически регистрирует нового пользователя в конкретном Firebase Auth проекте, повторный вход в этом же проекте с той же Google-учётной записью восстанавливает его UID. Новому профилю устанавливается publicStats=false; электронный адрес нельзя автоматически публиковать в качестве псевдонима. Изменение настроек профиля не изменяет число выученных слов. Чужие приватные словари, статистика и email не должны быть доступны другим.

Администратор получает пункт «Данные → Настройки сайта» только после серверной проверки Firebase custom claims. У остальных обычные разделы «Библиотека» и «Данные» остаются доступными.

## Два проекта: очень важное различие

Рабочий сайт https://sanastoyhteiso.github.io/ уже использует Firebase проект riveria-sanasto-community-test. Он рабочий, несмотря на слово test в имени. Не менять в нём ни Authentication, ни пользователей, ни Security Rules, ни результаты.

Экспериментальный сайт https://velardream-ctrl.github.io/riveria-sanasto-community-test/v3-classic/ пока имеет синтетический вход и запрещённые сетью операции. Будущий реальный пилот нуждается в совершенно новом независимом проекте Firebase с именем sanastoyhteiso-v3-* и отдельными тестовыми пользователями.

UID Firebase отличается между проектами. Даже один и тот же Google-аккаунт на отдельном Firebase тестовом проекте получит другой UID. Поэтому тестовая регистрация не является переносом рабочего аккаунта.

При финальном переходе на новый основной сайт рекомендуем сохранить действующий production Firebase Auth проект, чтобы не менять идентификаторы существующих пользователей. Отдельный тестовый Firebase служит только для разработки. Если когда-либо понадобится заменить Auth проект, нужен отдельный согласованный перенос пользователей с доказуемым сопоставлением UID и свежими резервными копиями.

## Что подготовлено без сетевых операций

1. staging/backend/rs-v3-auth-controller.js — независимый ES5 контроллер Google-входа, verified/unverified, подтверждения email, выхода, переключения аккаунтов и безопасной выдачи ID token только проверенному UID. Google popup инициируется синхронно настоящим нажатием для Safari. Токены не записываются и не выводятся в UI.
2. staging/backend/rs-v3-firebase-compat-auth.js — инжектируемый адаптер compat Firebase SDK. До любых SDK действий требует успешную проверку нового отдельного проекта через v3-staging-project-guard.js.
3. staging/backend/rs-v3-profile-contract.js — контракт Firestore профиля с полями alias/publicStats/learned/updatedAt, совместим с прежним форматом. Новые профили закрыты по умолчанию, повторный вход не затирает старый профиль, псевдоним не равен email.
4. staging/tests/v3-auth-isolation.test.cjs — проверки двух вымышленных пользователей, подписи Auth, отсутствия токенов в UI, отказа старому Firebase, Google sign-in, token race, sign-out.
5. staging/tests/v3-profile-registration.test.cjs — проверка приватной регистрации, повторного входа, смены псевдонима, сохранения learned, переключения аккаунтов, повреждённого профиля и неподтверждённого email.

Эти модули только в черновом PR #8. Они не подключены к рабочему сайту и ещё не используются в публичной демонстрационной версии. Все проверки выполняются с имитацией SDK и Firestore.

## Дальнейшие условия

Создать совершенно новый Firebase Auth/Firestore test project, настроить Google provider и Authorized domains для velardream-ctrl.github.io, настроить серверные Rules и проверить изоляцию чужих UID. Лишь после этого соединить новый контроллер с экраном входа, подобным нынешнему family-gate, и провести реальные испытания iPhone и Safari iOS12, включая popup, постоянную сессию, offline и смену пользователя на общем устройстве.

При финальном запуске сохранить настоящий Firebase Auth/UID, сделать свежие персональные JSON/Sheets резервные копии и провести тестированную миграцию словарей и результатов с откатом. Не удалять рабочие аккаунты и не переносить данные в тестовую базу без отдельного решения владельца.
