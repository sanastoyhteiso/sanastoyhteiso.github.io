# Sanastoyhteisö 3.0 — контракт диагностики ТЕХНИЧЕСКИХ неисправностей сайта

**RUN-20261107-120. Решение владельца от 07.11.2026. Приоритет для Stage D/E/H.**

## Смысл требования
Владелец хочет видеть в защищённой админ-панели **сбои самого сайта Sanastoyhteisö 3.0** на разных устройствах, чтобы находить причины и устранять их. Не следует путать «ошибки приложения, возникшие у пользователя» с «ошибками ученика в учебном задании». Последние не относятся к техническому мониторингу.

## Что считается техническим инцидентом
- JavaScript exception/unhandled rejection; белый экран, сломанный интерфейс, неработающая кнопка или зависшая загрузка.
- Сбой входа или обновления Firebase Auth, неожиданный отказ Firestore Security Rules.
- Сбой записи/чтения словаря, очереди V3, отправки/получения, конфликта или повторного проигрывания offline-событий.
- IndexedDB/local storage quota/несовместимость браузера, SW/cache mismatch, устаревшая версия, неожиданное падение UI.
- Отказы защищённого серверного сборщика, агрегатора, подтверждения резервной копии, восстановления или контрольного heartbeat.
- Потеря доступа к необходимому ресурсу / превышение времени запроса, с различением обычного offline и неисправности: **отсутствие интернета не является автоматически ошибкой**.

## Что категорически НЕ является техническим инцидентом
- Неправильный вариант ответа, ошибка при изучении слова, низкий балл, количество попыток, забытое слово.
- Нормальное изменение прогресса, создание своих слов, редактирование словаря, прохождение теста или использование Mediatri.
- Успеваемость, личная история ответов, результаты отдельных учеников. Эти данные не нужны для журнала сбоев.

## Требования к сбору и просмотру
1. Только allowlisted технический код (например, APP_RENDER_FAILED, SYNC_DOWNLOAD_FAILED), категория/уровень, время с минимально необходимой точностью, версия релиза, нормализованный тип браузера/платформы, технический этап или раздел без URL/параметров. Нельзя отправлять raw exception, stack, токены, UID, email, свободный текст, тексты ответов, словарные записи или пациентские сведения.
2. Коды ошибок группируются и дедуплицируются; в `/admin/` доступны тип сбоя, частота, первая/последняя встреча, версия, браузер, статус `новая → подтверждена → исправляется → исправлена → проверена`, ссылка на GitHub Issue/PR. Анонимная агрегированная статистика — без раскрытия учётных записей.
3. Собирать **технические сбои с устройств пользователей** и контрольные сигналы работоспособности сбора. Отказы самой телеметрии показывать как «Нет данных/Мониторинг недоступен», а не «Ошибок нет» или «ОК». При отсутствии связи допустить ограниченную локальную очередь с TTL/retry; при сбое сбора обучение не останавливать.
4. Нужны детерминированные тестовые неисправности на TEST, приёмка двух устройств/браузеров, проверка передачи только разрешённых технических кодов и отсутствие записей учебных результатов. Проверить Security Rules клиентских SDK, квоты, ограничение частоты, retention, отсутствие доступа обычного пользователя к админской сводке.
5. Для исправления — воспроизвести технический сбой, создать/связать Issue, исправить в DRAFT PR, протестировать, и после безопасного выпуска убедиться по мониторингу, что **именно этот тип сбоя** больше не повторяется; ноль событий не является доказательством при сломанной телеметрии.
