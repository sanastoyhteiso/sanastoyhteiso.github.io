## 1. Неподвижные границы и цель

**Цель:** единый сайт `https://sanastoyhteiso.github.io/` с FI/RU/EN, карточками, тестами, словарями и Mediatori; надёжным входом и отдельными пользовательскими историями; устойчивой автоматической синхронизацией Firestore/офлайн; независимыми закрытыми резервами Sheets/Drive и проверенным восстановлением; отдельной админ-панелью (наблюдаемость/ошибки/backup/release); процессом обновления одним ZIP через проверку, тестовый PR, CI, выпуск и откат.

**Без отдельного GO владельца не выполнять:** любой merge/deploy в production `main` или изменение LIVE Firebase `riveria-sanasto-community-test`; удаление/миграция чужих данных; платный Firebase/сервер/подписка, создание платёжных обязательств; публикация приватных данных или секретов; изменение чужих Firebase-аккаунтов/ролей; отключение защиты. TEST Firebase `sanastoyhteiso-v3-development` и TEST PR тоже не менять вслепую: прежде всего отдельный безопасный тест, read-only аудит, проверка текущего правил и объёма разрешений. Облачные записи, влияющие на реальные аккаунты, требуют предусмотренного отдельного разрешения.

**Неприкосновенность:** аккаунты, UID, прогресс остальных учеников, существующие private Sheets/Drive копии, работающие функции и бесплатный Spark. Участие владельца в потерях **своей** статистики никогда не заменяет согласия других учеников.

## 2. Новый рабочий метод: исполнитель действует без постоянных вопросов

1. Каждый ChatGPT/Work в начале сверяет последние RUN/TASK, точные HEAD PR #3/#8/#9, CI и критический путь. Повторно не обсуждать уже принятые решения и не давать пользователю копировать инструкции, если есть подключённый инструмент для законного действия.
2. Выбрать **одну проверяемую атомарную задачу** с максимальным эффектом для следующего gate. Сохранить `НАЧАЛ` в RUN-журнале до действия с веткой/SHA; выполнить; сохранить маленький проверенный commit/PR/CI; прочитать обратно; дописать `ЗАВЕРШИЛ`, либо честный ERROR/BLOCKED. После TASK — MASTER + Issue #10. История append-only.
3. Продолжать со следующей **независимой** задачей даже при блокировке, если она не зависит от недоступного доступа. Не спрашивать «продолжать?» после штатного завершения, когда следующий шаг разрешён и безопасен.
4. Не держать большие непроверенные локальные наборы изменений. Частые малые тестовые коммиты и CI, особенно перед ограничением Work/обрывом браузера. Не смешивать параллельные записи в одну ветку: один писатель на branch в момент времени; при разных подзадачах — отдельные feature branches/PR и явная сверка base HEAD.
5. Общаться с владельцем **по исключениям**: одно короткое сообщение при реальном блокере и один общий пакет решений/действий после подготовки, вместо множества малых вопросов. Хранить `OWNER-ACTION QUEUE` ниже; каждую просьбу сопровождать точной безопасной инструкцией. Не показывать ID/почту/токены в публичных отчётах.
6. Метрики успеха — не число коммитов и не субъективный процент, а: фактически работающая функция, закрытые дефекты, reproducible CI, проведённый реальный сценарий, сохраняемость данных, проверенный rollback. Отдельно обозначать `PREPARED`, `CI_PASS`, `LIVE_TEST_PASS`, `RELEASED`.

## 5. Минимум качества перед любым продвижением

- Security: deny-by-default, account switch fail-closed, запрет admin читателю без claim, no secret in Pages/public repo, data-minimization/retention, запрет cross-UID; реальные Rules сравниваются с полной текущей конфигурацией, не с урезанным fixture.
- Data: не терять чужие записи; независимый private backup имеет timestamp/hash, verify и restore drill; idempotent offline journal; миграция только после read-back.
- UI: FI/RU/EN, iOS12 Safari baseline, мобильная нижняя навигация и перенос длинных строк; no admin widgets в учебных «Данных»; не вводить ложный `ОК` при отсутствии данных.
- Release: CI + тест реального сценария, SHA manifest, rollback, owner GO; при красном CI/status не форсировать merge.
- Governance: журнал START→END, TASK MASTER, Issue #10, ссылки SHA, ни одной обобщённой галочки A–K без всех критериев.
