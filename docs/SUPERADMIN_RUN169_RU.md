# RUN169 — Superadmin: реестр зарегистрированных пользователей и журнал активности

## НАЧАЛ — 08.11.2026
- Владелец запросил защищённый режим суперадминистратора: реестр Firebase Authentication с email и датами регистрации/входа, журнал реальных посещений и учебных действий в существующем админ-меню.
- Исходный production main: `28addecbbd34f1ac534bd5d7515d92bb62aa5997`. Резервная ветка `backup/pre-superadmin-run169-20261108`; рабочая `feat/superadmin-directory-run169-20261108`.
- Причина отдельного бэкенда: обычный JS сайта не имеет законного доступа к перечню email/всех Firebase Auth пользователей. Только сервер с проверенным JWT, `admin=true`, конкретным `SUPERADMIN_UID` и ограниченным Google IAM правом `firebaseauth.users.get` может читать только нужные поля. Service account credentials — **только Secret Cloudflare**, никогда в GitHub или браузере.
- Дополнительный D1-журнал новых добровольно отмеченных посещений: одно событие каждого вида на пользователя в сутки, без паролей, IP, UID, email, URL, текстов слов, ответов и оценок в базе D1. Backend объединяет активность с реестром по HMAC-псевдониму, а не через копирование email в журнал.
- Контроллеру сайта нужны назначение цели, прозрачная политика конфиденциальности и сроки хранения; «режим бога» не должен предоставлять скрытую подмену пользователей, чтение приватных экзаменационных ответов или незаметное удаление записей. Модуль только read-only. Отдельная возможность администрирования аккаунтов требует самостоятельного согласования и server-audit.
- Безопасность: backend защита и учёт доступа обязательны; если нет учётных данных/миграции D1, UI честно показывает «Не подключено». Никаких реальных пользовательских email и ответов в тестах.
- Не изменять Firestore Rules, Firebase/Auth/права/IAM/тариф и основной сайт до тестов и отдельной ручной настройки бэкенда.
- Статус **НАЧАЛ**. Публикация запрещена до успешных CI, настройки Cloudflare, проверки негативных тестов, новой политики, подтверждения владельца и успешной загрузки данных в защищённой админке.
